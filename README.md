## Граф и формат файлов

Первая строка: `n m directed|undirected`. Затем ровно `m` строк `u v w`.
Вершины нумеруются от `0` до `n-1`, вес — любое значение `int`, в том числе отрицательное.

```text
3 2 undirected
0 1 4
1 2 -2
```

`Graph.read(Path)` читает UTF-8. Между полями допустимы пробелы и табуляции,
после последнего ребра допустимы пустые строки. Комментарии, пустые строки
внутри данных, лишние рёбра, неверные номера вершин и числа вне диапазона `int`
отклоняются с `IOException` и пояснением. Для программного добавления некорректных
вершин используется `IllegalArgumentException`.

`Graph.edges()` содержит каждое добавленное ребро один раз. Для неориентированного
графа `neighbors(u)` содержит направления к соседям: ребро `u-v` добавляет две
записи, даже если `u == v`. Поэтому сумма размеров списков смежности равна `2m`,
а для ориентированного графа — `m`. Петли и параллельные рёбра сохраняются;
изолированные вершины имеют пустые списки. Списки доступны только для чтения,
изменения графа выполняются через `addEdge`.

В тестах используются все три исходных файла из `data/`. В несвязном примере есть
параллельные рёбра, петли и две изолированные вершины. В ориентированном примере
есть цикл `0 -> 1 -> 2 -> 0`, цикл `3 -> 4 -> 3` и изолированная вершина `5`.

Дополнительно `data/dag-directed.txt` задаёт DAG с источниками `4`, `5`, `6`,
параллельными рёбрами `4 -> 1` и отрицательными весами. Вершина `6` изолирована.
Этот четвёртый файл используется в тестах Kosaraju, Kahn и кратчайших путей.

## DSU и счётчики

`DSU(n)` вызывает `makeSet(n)` и создаёт `n` отдельных множеств. `find(x)` находит
корень итеративно, затем перенаправляет каждую вершину пройденного пути прямо к
корню. `union(x, y)` присоединяет меньшее дерево к большему и возвращает `true`
только при объединении разных компонент. `components()` возвращает их число.

- `findCalls`: один за каждый корректный вызов `find`, включая два вызова внутри
  каждого `union`. Переходы по родителям внутри `find` отдельно не считаются.
- `successfulUnions`: один только за объединение разных компонент.
- `dsuOps = findCalls + successfulUnions`.
- Неуспешный `union` вызывает два `find`, но не увеличивает `successfulUnions`.
- Некорректные аргументы отклоняются до изменения структуры или счётчиков.
- `resetCounters()` обнуляет измерения, сохраняя множества; `makeSet(n)` пересоздаёт
  множества и также обнуляет счётчики. Тип счётчиков — `long`.

Например, `union(0, 1)` у двух отдельных вершин даёт `findCalls = 2`,
`successfulUnions = 1`, `dsuOps = 3`. Повторный `union(0, 1)` увеличит
`dsuOps` до `5`, а число компонент не изменится.

Инициализация занимает `O(n)` времени и памяти. `find` и `union` имеют
амортизированную стоимость `O(α(n))` при совместном применении обеих оптимизаций.
Это оценка последовательности операций, а не обещание строго константного
времени каждого отдельного вызова. Дополнительная память одного вызова — `O(1)`;
`components()` также выполняется за `O(1)`.

## Минимальный остовный лес: Kruskal и Prim

`Kruskal.compute(graph)` и `Prim.compute(graph)` возвращают `MstResult`:
`edges()` — неизменяемый список рёбер леса, `totalWeight()` — суммарный вес `long`,
`components()` — число компонент, включая изолированные вершины.
Для пустого графа результат содержит ноль рёбер, вес 0 и ноль компонент.
Оба алгоритма отклоняют ориентированный граф с поясняющим `IllegalArgumentException`.

Kruskal сортирует копию списка рёбер по весу, затем проверяет концы через DSU.
Ребро добавляется, только если оно соединяет разные компоненты. Когда остаётся
одна компонента, просмотр прекращается; на несвязном графе просматриваются все
рёбра. Сортировка всегда обрабатывает полный список и не меняет исходный граф.

Prim начинает с вершины 0, если она существует. В `PriorityQueue` находятся рёбра
от посещённых вершин к ещё не посещённым. При извлечении ребра алгоритм проверяет,
не была ли его конечная вершина уже добавлена другим ребром. Когда очередь
опустеет, алгоритм начинает следующую компоненту с первой непосещённой вершины.
Петли не добавляются в лес, параллельные и отрицательные рёбра допустимы.

Сравнение весов выполняется через `Integer.compare`, без вычитания с риском
переполнения; суммарный вес хранится в `long`. У каждого леса ровно
`n - components` рёбер. При одинаковых весах конкретные деревья могут отличаться.

Для `data/connected-undirected.txt` оба алгоритма возвращают вес **10**, одну
компоненту и 4 ребра. Для `data/disconnected-undirected.txt` — вес **8**, четыре
компоненты и 3 ребра; отрицательные петли не уменьшают вес леса.

Kruskal использует `O(n + m log(m+1) + m α(n))` времени с учётом инициализации
DSU и `O(n + m)` дополнительной памяти. Для связного графа обычно записывают
`O(m log m)`. В этой реализации Prim очередь хранит рёбра, поэтому время равно
`O(n + m log(m+1))`, дополнительная память — `O(n + m)`. Наличие параллельных
рёбер не позволяет без дополнительных оговорок заменить `log m` на `log n`.
В память включены рабочие структуры и возвращаемый лес, исходный граф не включён.

## Счётчики MST

Варианты `compute(graph, metrics)` принимают `metrics.Metrics` и сбрасывают
все его поля перед каждым корректным запуском. Каждый алгоритм создаёт новые
рабочие структуры; повторный запуск не продолжает предыдущий.

| Поле | Kruskal | Prim |
| --- | --- | --- |
| `dsuOps` | Фактический счётчик DSU: вызовы `find` плюс успешные `union` | 0 |
| `edgeScans` | Кандидаты, проверенные после сортировки до остановки | Все записи списков смежности, включая петли и обратные направления: `2m` |
| `comparisons` | Вызовы сравнения весов при сортировке | Вызовы сравнения весов внутри очереди при добавлении и извлечении |
| `maxDepth` | 0, явный стек DFS не используется | 0, очередь не считается стеком DFS |

В Kruskal проверка концов делает два `find`. Для принятого ребра `union` делает
ещё два `find` и увеличивает счётчик успешных объединений. Итого принятое ребро
даёт 5 DSU-операций, отклонённое — 2. Эти числа не подставляются по формуле:
счётчики увеличивает сам DSU, а Kruskal читает их итог.

Копирование списка рёбер, инициализация массивов и проверка типа графа не входят
в `edgeScans` или `comparisons`; их стоимость включена в оценку сложности.
Извлечение устаревшего ребра в Prim не увеличивает `edgeScans`, но сравнения
весов при работе очереди учитываются. Поэтому `edgeScans` сам по себе не измеряет
всю работу MST. В частности, логарифмический множитель сортировки Kruskal виден
в `comparisons`, а не обязательно в числе просмотренных кандидатов.
Точные числа сравнений зависят также от реализации сортировки и очереди JDK.
Измерение времени и общий CSV реализованы в `benchmark.Benchmark`.

## Компоненты сильной связности: Kosaraju

`Kosaraju.compute(graph)` возвращает `SccResult`: `componentCount()` — число
компонент, `componentOf(vertex)` — номер компоненты вершины,
`componentIds()` — копия массива номеров. Номера лежат в диапазоне
`0 .. componentCount-1`; их конкретные значения не являются частью смысла
разбиения. Для проверки принадлежности одной компоненте сравниваются номера
двух вершин, а для сравнения разных алгоритмов — состав компонент.

Первый DFS проходит исходный граф и записывает вершину в порядок завершения
только после обработки всех её исходящих рёбер и потомков. Массив `stack`
хранит текущий путь обхода, а `nextEdge[vertex]` — индекс следующего ребра,
к которому нужно вернуться после обхода потомка. Затем строится отдельный граф
с обращёнными рёбрами. Второй DFS рассматривает вершины в обратном порядке
завершения первого прохода и назначает одной компоненте все вершины своего дерева.

Оба прохода итеративные и не используют рекурсию. Петли и параллельные рёбра
сохраняются и обрабатываются; веса не влияют на достижимость. Изолированная
вершина образует отдельную компоненту. Для пустого графа число компонент равно 0.
Неориентированный граф отклоняется с `IllegalArgumentException`.

В примере `data/cyclic-directed.txt` компоненты равны `{0,1,2}`, `{3,4}` и `{5}`.
Алгоритм работает за `O(n + m)` времени. Дополнительная память — `O(n + m)`:
обратный граф требует `O(n + m)`, массивы порядка, посещения, компонент и стека —
`O(n)`. Построение обратного графа входит в эту оценку.

## Топологическая сортировка: Kahn

`Kahn.compute(graph)` возвращает массив всех вершин в допустимом порядке.
Сначала алгоритм считает входящие степени и помещает все вершины с нулевой
степенью в `ArrayDeque`. Извлечённая вершина добавляется в ответ, входящие степени
её соседей уменьшаются; сосед попадает в очередь в момент достижения нуля.
Параллельные рёбра учитываются по отдельности и при подготовке, и при уменьшении
степени. Отрицательные веса не влияют на порядок.

Если извлечено меньше `n` вершин, метод выбрасывает `IllegalArgumentException`
с сообщением о цикле, не возвращая частичный порядок. Это относится и к петле,
и к циклу в отдельной компоненте. Пустой ориентированный граф даёт пустой порядок;
неориентированный граф отклоняется независимо от наличия рёбер.

`Kahn.isValidOrder(graph, order)` независимо проверяет длину, диапазон номеров,
отсутствие повторов и условие `position[u] < position[v]` для каждого ребра.
Изолированные вершины тоже обязаны присутствовать. Проверка принимает любой
корректный порядок, а не только тот, который выдаёт текущая очередь.

Время сортировки — `O(n + m)`, дополнительная память — `O(n)`.
В эти оценки входят подготовка входящих степеней, очередь и возвращаемый массив.
Проверка порядка отдельно требует `O(n + m)` времени и `O(n)` памяти.

## Счётчики обходов и подготовительная работа

Kosaraju и Kahn принимают необязательный аргумент `Metrics`, как алгоритмы MST.
На каждом корректном по типу графа вызове все счётчики сбрасываются. Веса не
сравниваются, DSU не используется, поэтому `comparisons` и `dsuOps` равны 0.

| Алгоритм | `edgeScans` | Подготовка вне этого счётчика | `maxDepth` |
| --- | --- | --- | --- |
| Kosaraju | `2m`: каждое ребро в каждом из двух DFS | Построение обратного графа просматривает ещё `m` рёбер; инициализация массивов | Максимальное число активных вершин в стеке одного DFS, максимум по обоим проходам |
| Kahn на DAG | `m`: исходящие рёбра извлечённых вершин | Начальное вычисление входящих степеней просматривает ещё `m` рёбер | 0: очередь не является стеком DFS |

Счётчики увеличиваются при фактическом рассмотрении ребра, значения `m` и `2m`
не присваиваются по формуле. У Kosaraju `maxDepth` измеряется в вершинах, включая
корень: для пустого графа это 0, для непустого графа из изолятов — 1, для пути
`0 -> 1 -> ... -> 99999` — 100 000. Это длина текущего пути DFS в выбранном порядке
обхода, а не размер выделенного массива, не сумма глубин двух проходов и не
длина самого длинного пути произвольного графа. Значение может зависеть от
порядка рёбер; размер стека ограничен `n`, поскольку вершина помечается при добавлении.

На циклическом графе Kahn может просмотреть меньше `m` рёбер до ошибки:
недоступные для очереди вершины не обрабатываются. Требование ровно `m` относится
к успешно обработанному DAG. `isValidOrder` выполняет отдельную проверку и не
меняет метрики сортировки. Подготовка выполняется внутри `compute`, поэтому
замер всего вызова учитывает её время; линейная оценка сложности
уже включает подготовку, даже когда счётчик отражает только основной обход.

## Кратчайшие пути в DAG

`DagShortestPath.compute(graph)` возвращает `PathResult` с расстояниями `long`
и массивом предшественников `parent`. Сначала Kahn получает топологический порядок
и отклоняет любой цикл, включая петлю и цикл в отдельной компоненте. Затем
расстояния **всех** вершин с входящей степенью 0 устанавливаются в 0, остальных —
в `INFINITY = Long.MAX_VALUE`. Это модель виртуального общего источника с
нулевыми рёбрами только к источникам исходного графа; отдельная вершина в Graph
для него не создаётся. Изолированные вершины также являются источниками.

Вершины обрабатываются в топологическом порядке. Для каждого ребра `u -> v`
вычисляется `candidate = distance[u] + weight`; если кандидат меньше текущего
расстояния `v`, обновляются расстояние, родитель и выбранное ребро.
С бесконечностью вес не складывается. В конечном DAG каждая вершина достижима
из некоторого источника, поэтому после успешного прохода все расстояния конечны.
В момент обработки вершины все её предшественники уже обработаны, а значит,
её расстояние окончательно: повторять проход релаксаций не нужно.

Отрицательные веса допустимы. Они допустимы и в общих графах, например для
Bellman–Ford, но достижимый отрицательный цикл позволяет неограниченно уменьшать
вес пути к вершинам, достижимым из него. В DAG циклов нет, поэтому этой проблемы
не возникает, а топологический порядок даёт линейный алгоритм.

Методы `PathResult`:

- `distanceTo(v)` и `parentOf(v)` — расстояние и предшественник; у источника
  расстояние 0, родитель `-1`.
- `distances()` и `parents()` — защитные копии массивов.
- `pathTo(v)` — неизменяемый список вершин от выбранного источника до `v`.
  Для самого источника список содержит одну вершину.
- `edgePathTo(v)` — неизменяемый список конкретных рёбер того же пути. Массив
  `parentEdge` сохраняет выбранное ребро, потому что одного `parent` недостаточно
  для различения параллельных рёбер с разными весами.
- `sumDistances()` — сумма расстояний для столбца `result` в CSV.
  Каждое сложение проверяется через `Math.addExact`; выход промежуточной суммы
  из диапазона `long` вызывает `ArithmeticException` вместо неверного результата.
- `vertexCount()` — количество вершин в результате. Методы доступа по вершине
  проверяют её номер и отклоняют выход за границы.

На равных расстояниях уже выбранный путь сохраняется; конкретный путь среди
равноценных не гарантирован. Восстановление идёт итеративно по родителям и затем
разворачивает список, поэтому не зависит от глубины стека вызовов Java.

Для `data/dag-directed.txt` расстояния в порядке вершин `0..6` равны
`[-2, -2, 1, 0, 0, 0, 0]`, их сумма равна **-3**. Путь к вершине `3`:
`4 -> 2 -> 0 -> 3`, веса рёбер `1, -3, 2`, итоговый вес **0**.
К вершине `1` выбирается параллельное ребро `4 -> 1` с весом **-2**.

Время `compute` — `O(n + m)`, дополнительная память — `O(n)` с учётом
топологического порядка, рабочих массивов и результата. Отдельное расстояние
помещается в `long`: простой путь DAG содержит не более `n-1` рёбер с весами `int`.
Восстановление пути из `k` вершин занимает `O(k)` времени и памяти;
суммирование расстояний — `O(n)` времени и `O(1)` дополнительной памяти.

## Счётчики кратчайших путей

`DagShortestPath.compute(graph, metrics)` сбрасывает переданные метрики и
считает только основной проход релаксаций:

| Поле | Что считается |
| --- | --- |
| `edgeScans` | Одно увеличение при обработке каждого ребра: ровно `m` на DAG |
| `comparisons` | Одно сравнение суммарного веса кандидата с лучшим расстоянием: ровно `m` |
| `dsuOps` | 0: DSU не используется |
| `maxDepth` | 0: явного стека DFS нет |

Топологическая сортировка вызывается с отдельными метриками. Весь вызов
`DagShortestPath.compute` включает четыре прохода по рёбрам: подсчёт входящих
степеней внутри Kahn, проход очереди Kahn, повторный подсчёт степеней для
инициализации источников и релаксации. Первые три не входят в `edgeScans`
кратчайших путей, но их стоимость входит во время вызова и оценку `O(n + m)`.
Повторный подсчёт оставлен явно, чтобы алгоритм не зависел от внутренних массивов
Kahn. Чтение или генерация исходного графа выполняются до вызова алгоритма.
Восстановление путей и `sumDistances()` — отдельные операции после `compute`.
При цикле ошибка возникает до начала релаксаций, поэтому их счётчик равен 0.

## Тестирование

`GraphTest` проверяет три файла, направление рёбер, петли, параллельные рёбра,

Отдельно проверяются счётчики, сброс, ошибки аргументов и 100 000 элементов.

и **50 несвязных** (seed 2026). Проверяются совпадение веса, число компонент и
число рёбер. Независимая проверка через BFS подтверждает, что лес использует
рёбра исходного графа и соединяет в точности те же компоненты. Вместе с условием
`n - components` это исключает циклы в результате.

Для **60 маленьких мультиграфов** (seed 99, до 6 вершин и 10 рёбер) ожидаемый

пустой граф, петли, параллельные рёбра, изоляты, отрицательные и крайние веса,

`KosarajuTest` сравнивает результат со взаимной достижимостью через BFS из каждой

`KahnTest` проверяет **100 случайных DAG** с перемешанными номерами вершин

изолированные вершины, параллельные рёбра, петля, цикл в отдельной компоненте,
ошибочные входы валидатора порядка и повторные запуски со сбросом метрик.

`DagShortestPathTest` сравнивает расстояния с Bellman–Ford на **100 случайных DAG**
с `n <= 40`, перемешанными номерами вершин, параллельными рёбрами и весами
от -100 до 100 (seed 424242). Эталон также начинает с расстояния 0 у всех источников,
но выполняет до `n-1` полных проходов по рёбрам без топологической сортировки.

Отдельные тесты проверяют известный файл, пустой граф, изоляты, несколько источников

## Бенчмарк, CSV и графики

`GraphGenerator.generate(n, m, kind)` создаёт каждый граф с новым `Random(42)`.

## Бонус: Tarjan SCC

`Tarjan.compute` выделяет SCC за один итеративный DFS, без обратного графа.
`index[v]` — номер открытия вершины, `lowlink[v]` — минимальный индекс, достижимый
по дереву DFS и допустимой ссылке на активную вершину. При возврате от потомка
его `lowlink` передаётся родителю. Ребро к уже завершённой SCC не уменьшает
`lowlink`; для ребра к активному соседу используется его `index`.
При `lowlink[v] == index[v]` из стека активных вершин снимается одна SCC до `v`.

Есть два массива стека: текущий путь DFS и вершины ещё не закрытых SCC.
`maxDepth` измеряет только текущий путь DFS, как у Kosaraju, а не размер второго
стека. `edgeScans = m`, сравнения весов и DSU-операции равны 0. Время `O(n+m)`,
дополнительная память `O(n)`. `SccResult.samePartitionAs` сравнивает разбиения
через взаимно однозначное соответствие меток за `O(n+c)`, не сравнивая номера напрямую.

`TarjanTest` сверяет результат с Kosaraju на двух файлах, 100 случайных графах
(seed 98765), петлях, параллельных рёбрах, изолятах, пути и цикле из 100 000 вершин.
`BonusBenchmark` делает пять запусков Tarjan на каждой из 10 конфигураций
ориентированного генератора и сверяет полный состав компонент с Kosaraju.
Время — медиана; валидация вне таймера. `results/bonus.csv` отделён от обязательных
50 строк. Tarjan просматривает `m` рёбер против `2m` в DFS Kosaraju; кроме того,
ему не требуется проход для построения обратного графа.

## Бонус: конденсация и критический путь

`Condensation.build` объединяет каждую SCC в вершину DAG, удаляет внутренние
рёбра и оставляет одну зависимость на каждую пару компонент. Если бы в таком
графе был цикл, все его компоненты были бы взаимно достижимы и являлись бы одной SCC.

**Модель:** каждая исходная вершина — единица работы; SCC — неделимый блок
длительностью, равной числу её вершин. Межкомпонентные рёбра — зависимости
с нулевой задержкой. Исходные веса рёбер намеренно не используются как длительности.
Сжатие цикла само по себе не решает реальный deadlock: модель предполагает, что
внутренний цикл уже разрешён или группа выполняется как единый блок.

`CriticalPath.compute` обрабатывает конденсацию в порядке Kahn. У источника
`finish = duration`; на ребре `u -> v` выполняется
`finish[v] = max(finish[v], finish[u] + duration[v])`. Из вершины с наибольшим
временем завершения восстанавливается путь по родителям. Результат содержит
`duration()`, защитную копию `finishTimes()` и неизменяемый `componentPath()`.
Для пустого графа длительность равна 0 и путь пуст. Это длина критической цепочки
при неограниченном параллелизме, а не сумма времени всех независимых блоков.

Построение конденсации с Tarjan занимает ожидаемое `O(n+m)` время и `O(n+m)`
дополнительную память с учётом `HashSet` для устранения повторов. При `c` компонентах
и `e` уникальных зависимостях критический путь требует `O(c+e)` времени и `O(c)`
дополнительной памяти. Для конденсации `edgeScans=e`, `comparisons=e+max(c-1,0)`:
релаксации плюс выбор конечной вершины. Подготовка Kahn и источников учитывается
во времени, но не в счётчике релаксаций.

`CriticalPathTest` проверяет известный пример, пустой граф, изоляты, одну SCC,
100 случайных графов с полным перебором путей в небольших конденсациях и цепочку
из 100 000 вершин. В `BonusBenchmark` путь дополнительно сверяется с кратчайшими
путями после смены знака длительностей и добавления виртуального источника.
Проверяются все времена завершения, итоговая длина и восстановленная цепочка.

`results/bonus.csv` содержит **20 строк**: по одной для Tarjan и CriticalPath
на каждую исходную конфигурацию. Для CriticalPath колонки `n,m` относятся к
конденсации, исходные размеры указаны в поле `graph`, например
`condensation_from_1000_4000`. Таймер этой строки включает построение конденсации,
Kahn и поиск пути; вычисление SCC выполнено ранее и измерено строкой Tarjan.
Каждая бонусная операция измеряется пять раз, записывается медиана, проверки
выполняются вне таймера. Обязательные 50 строк остаются в отдельном файле.

**Классы и методы:** `Graph`, `Edge`; `Graph.read`, `addEdge`, `neighbors`,
`edges`, `vertexCount`, `edgeCount`, `isDirected`.

**Задача:** хранить вершины и взвешенные рёбра в одном типе графа.
У каждой вершины есть список исходящих рёбер. Для неориентированного ребра
добавляется и обратное направление, а общий список сохраняет ребро один раз.
Чтение файла проверяет формат и допустимость номеров вершин.

**Термины:** список смежности — рёбра, выходящие из вершины; петля — ребро в ту же
вершину; параллельные рёбра — несколько рёбер с одинаковыми концами; изолированная
вершина — вершина без инцидентных рёбер.

**Что объяснить:** как один класс поддерживает оба типа графа, зачем нужен
отдельный список рёбер, как хранятся петли и почему объём памяти равен `O(n + m)`.

**Вопросы преподавателя:**

1. Почему у неориентированного графа `2m` записей смежности? Каждое ребро доступно
   с обоих концов; петля тоже даёт две записи.
2. Почему `edgeCount()` не возвращает `2m`? Он считает добавленные рёбра в общем списке.
3. Как хранится изолированная вершина? Её список смежности пуст, но сама вершина существует.
4. Можно ли добавить отрицательный вес? Да, граф хранит любой `int`; ограничения
   конкретного алгоритма проверяются в этом алгоритме.
5. Что будет при лишнем ребре в файле? `read` сообщит об ошибке через `IOException`.

### DSU — множества, find, union и обе оптимизации

**Файлы для копирования в чат:** `src/main/java/algorithms/DSU.java`,
`src/test/java/algorithms/DSUTest.java` и раздел «DSU и счётчики» этого README.

**Классы и методы:** `DSU`; `makeSet`, `find`, `union`, `components`,
`findCalls`, `successfulUnions`, `dsuOps`, `resetCounters`;
`DSUTest.matchesSimpleReferenceAfterEveryRandomUnion`.

**Задача:** быстро определять, принадлежат ли две вершины одному множеству,
и объединять множества. Множество представлено деревом родителей с одним корнем.
`find` сжимает путь до корня, а `union` присоединяет меньшее дерево к большему.
Число компонент уменьшается только при успешном объединении.

**Термины:** представитель — корень дерева множества; сжатие пути — перенаправление
родителей к корню; union by size — присоединение меньшего дерева к большему;
амортизированная оценка — средняя стоимость операции в последовательности;
`α(n)` — очень медленно растущая обратная функция Аккермана.

**Что объяснить:** изменения `parent` и `size` на примере четырёх вершин, совместную
роль двух оптимизаций, смысл каждого счётчика и сравнение с простым эталоном.

**Вопросы преподавателя:**

1. Зачем нужны обе оптимизации? Объединение по размеру ограничивает рост деревьев,
   а сжатие ускоряет последующие поиски на уже пройденных путях.
2. Почему повторный `union` возвращает `false`? Корни совпадают, новое множество не появляется.
3. Сколько операций считает успешный `union`? Два `find` и одно успешное объединение: три.
4. Почему в тестах нельзя просто сравнить номера корней с эталоном? Разные корректные
   реализации могут выбирать разных представителей того же множества.
5. Что сбрасывает `makeSet`? Все прежние объединения и счётчики; `resetCounters`
   сбрасывает только счётчики.

### KRUSKAL — сортировка рёбер и построение леса

**Файлы для копирования в чат:** `src/main/java/algorithms/Kruskal.java`,
`src/main/java/algorithms/DSU.java`, `src/main/java/algorithms/MstResult.java`,
`src/main/java/metrics/Metrics.java`, `src/test/java/algorithms/MstTest.java`.

**Классы и методы:** `Kruskal.compute`, `DSU.find`, `DSU.union`, `DSU.components`,
`MstResult.edges`, `MstResult.totalWeight`, `MstResult.components`.

**Задача:** соединить каждую компоненту графа рёбрами минимального суммарного веса.
Алгоритм рассматривает рёбра от лёгких к тяжёлым и добавляет ребро, только если
его концы принадлежат разным множествам DSU. На несвязном графе результатом
является несколько деревьев, включая отдельные изолированные вершины.

**Термины:** остовное дерево — связный граф на всех вершинах компоненты без циклов;
остовный лес — по дереву для каждой компоненты; разрез — разделение вершин на две
части; свойство разреза — минимальное ребро через подходящий разрез безопасно
добавить к строящемуся минимальному остову.

**Что объяснить:** порядок сортировки, роль DSU в обнаружении цикла, безопасный
выбор ребра через разрез, раннюю остановку и отличие `edgeScans` от `comparisons`.

**Вопросы преподавателя:**

1. Почему ребро между одинаковыми корнями не добавляется? Его концы уже соединены,
   поэтому добавление создаст цикл.
2. Почему минимальное ребро безопасно? Если оптимальное дерево его не содержит,
   заменяем ребро через тот же разрез на выбранное без увеличения веса.
3. Можно ли остановиться при `n-1` принятых рёбрах? Да, это одна компонента;
   на несвязном графе такое число недостижимо и просмотр продолжается до конца.
4. Почему мало измерить только `edgeScans`? Перед просмотром уже выполнена
   сортировка всех рёбер, её сравнения учитываются отдельно.

### PRIM — очередь с приоритетом и рост леса

**Файлы для копирования в чат:** `src/main/java/algorithms/Prim.java`,
`src/main/java/algorithms/MstResult.java`, `src/main/java/graph/Graph.java`,
`src/main/java/graph/Edge.java`, `src/main/java/metrics/Metrics.java`,
`src/test/java/algorithms/MstTest.java`.

**Классы и методы:** `Prim.compute`, `Prim.addEdges`, `Graph.neighbors`,
`MstResult.totalWeight`, `MstResult.components`.

**Задача:** вырастить минимальное дерево от начальной вершины.
Очередь хранит возможные рёбра к новым вершинам и выдаёт самое лёгкое.
Вершины помечаются при включении в дерево; устаревшие кандидаты пропускаются.
Для несвязного графа рост повторяется с новой непосещённой вершины.

**Термины:** очередь с приоритетом — структура для извлечения минимального элемента;
посещённая вершина — уже включённая в лес; устаревшее ребро — кандидат, конечная
вершина которого уже добавлена; граница дерева — рёбра между посещёнными и
непосещёнными вершинами.

**Что объяснить:** содержимое очереди на каждом шаге, пропуск устаревших рёбер,
обработку изолированной вершины 0 и выбор минимального ребра через разрез.

**Вопросы преподавателя:**

1. Почему нельзя принимать каждое извлечённое ребро? Его конечная вершина могла
   уже войти в дерево через другой кандидат.
2. Что происходит, если вершина 0 изолирована? Она образует отдельную компоненту,
   затем внешний цикл переходит к следующей непосещённой вершине.
3. Нужен ли DSU? Нет, принадлежность растущему дереву хранится в `visited`.
4. Почему память очереди может быть `O(m)`? Она хранит рёбра, в том числе несколько
   кандидатов к одной вершине и устаревшие кандидаты.
5. Должны ли рёбра совпасть с Kruskal? Нет, при равных весах решений может быть
   несколько; должны совпасть минимальный вес и компоненты.

### METRICS — правила подсчёта операций

**Файлы для копирования в чат:** `src/main/java/metrics/Metrics.java`,
`src/main/java/algorithms/DSU.java`, `src/main/java/algorithms/Kruskal.java`,
`src/main/java/algorithms/Prim.java`, `src/main/java/algorithms/Kosaraju.java`,
`src/main/java/algorithms/Kahn.java`, `src/main/java/algorithms/DagShortestPath.java`,
`src/test/java/algorithms/MstTest.java`, `src/test/java/algorithms/KosarajuTest.java`,
`src/test/java/algorithms/KahnTest.java`, `src/test/java/algorithms/DagShortestPathTest.java`
и разделы о счётчиках этого README.

**Классы и методы:** `Metrics.reset`, `DSU.dsuOps`, `Kruskal.compute`,
`Prim.compute`, `Prim.addEdges`, `Kosaraju.finishOrder`, `Kosaraju.assignComponents`,
`Kahn.compute`, `DagShortestPath.compute`, `MstTest.countsActualScansComparisonsAndDsuOperations`.

**Задача:** измерять выполненную алгоритмом работу по явным правилам.
Счётчики увеличиваются в местах выполнения операций, а перед новым запуском
сбрасываются. Для MST измеряются операции DSU, просмотры рёбер и сравнения весов;
для Kosaraju — два прохода и глубина явного стека, для Kahn — проход очереди,
для кратчайших путей — проход релаксаций.

**Термины:** счётчик — число выполненных операций определённого вида; граница
измерения — какие действия включены в подсчёт; `edgeScans` — просмотры по правилам
алгоритма; `comparisons` — сравнения весов, включая суммарные веса путей,
а не любые условия в коде.

**Что объяснить:** почему у Prim `2m` просмотров, почему сортировка не входит
в `edgeScans` Kruskal и почему счётчики одного запуска нельзя суммировать
с предыдущими при сравнении размеров графа.

**Вопросы преподавателя:**

1. Почему успешное ребро Kruskal даёт 5 DSU-операций? Два внешних `find`, два
   внутри `union` и одно успешное объединение.
2. Откуда берётся `2m` у Prim? Он один раз проходит список смежности каждой вершины,
   а каждое неориентированное ребро представлено двумя записями.
3. Почему `maxDepth` равен нулю? У MST нет явного стека DFS; размер очереди — другая величина.
4. Измеряет ли один счётчик всё время? Нет, например копирование и инициализация
   не считаются сравнениями весов, но входят в общую стоимость алгоритма.
5. Почему у Kosaraju `2m`, хотя строится обратный граф? Этот счётчик отражает
   только два DFS; ещё один проход при построении обратного графа описан отдельно.

### SCC — Kosaraju, обратный граф и два прохода

**Файлы для копирования в чат:** `src/main/java/algorithms/Kosaraju.java`,
`src/main/java/algorithms/SccResult.java`, `src/main/java/graph/Graph.java`,
`src/main/java/graph/Edge.java`, `src/main/java/metrics/Metrics.java`,
`src/test/java/algorithms/KosarajuTest.java`, `data/cyclic-directed.txt`.

**Классы и методы:** `Kosaraju.compute`, `finishOrder`, `reverse`,
`assignComponents`; `SccResult.componentOf`, `componentCount`, `componentIds`;
`KosarajuTest.assertMatchesReachability`.

**Задача:** разделить ориентированный граф на максимальные группы вершин,
внутри которых любая вершина достижима из любой другой.
Первый DFS определяет порядок завершения, второй обходит обратный граф
в убывающем порядке завершения и выделяет группы. Оба обхода используют массив
стека и индекс следующего ребра вместо рекурсивных вызовов.

**Термины:** SCC — компонента сильной связности; обратный граф — граф с обращённым
направлением каждого ребра; порядок завершения — порядок выхода из DFS после
обработки потомков; явный стек — самостоятельно хранимая последовательность
активных вершин обхода; взаимная достижимость — наличие путей в обе стороны.

**Что объяснить:** зачем обращать рёбра, почему нужен порядок завершения,
как `nextEdge` позволяет продолжить обход после возврата от потомка и почему
большой граф не переполняет стек вызовов JVM.

**Вопросы преподавателя:**

1. Почему недостаточно порядка первого посещения? Он не отражает завершение
   обхода потомков; во втором проходе можно ошибочно объединить разные SCC.
2. Почему второй DFS выделяет одну SCC? Среди оставшихся компонент выбранная
   имеет максимальное время завершения; в обратном графе из неё нельзя выйти
   в ещё не обработанную компоненту, но достижимы все вершины её собственной SCC.
3. Что означает `maxDepth = 100000`? В некоторый момент один стек содержал
   100 000 активных вершин пути DFS; это память массива, а не 100 000 вызовов Java.
4. Почему число просмотров равно `2m`? Каждый из двух полных DFS рассматривает
   каждую запись ориентированного списка смежности один раз.
5. Как сравниваются компоненты с эталоном? Для каждой пары вершин сравниваются
   равенство компонент и существование путей в обе стороны, а не номера меток.

### TOPO — Kahn, входящие степени и обнаружение цикла

**Файлы для копирования в чат:** `src/main/java/algorithms/Kahn.java`,
`src/main/java/graph/Graph.java`, `src/main/java/graph/Edge.java`,
`src/main/java/metrics/Metrics.java`, `src/test/java/algorithms/KahnTest.java`,
`data/dag-directed.txt`, `data/cyclic-directed.txt`.

**Классы и методы:** `Kahn.compute`, `Kahn.isValidOrder`, `Kahn.requireDirected`;
`KahnTest.assertOrder`, `throwsInsteadOfReturningPartialOrderWhenCycleIsDisconnected`.

**Задача:** расставить вершины так, чтобы начало каждого ребра шло раньше конца.
В очередь помещаются вершины без входящих рёбер из ещё не обработанной части.
При извлечении вершины её рёбра логически удаляются уменьшением входящих степеней.
Если очередь опустела до обработки всех вершин, алгоритм сообщает о цикле.

**Термины:** DAG — ориентированный граф без циклов; входящая степень — число
рёбер, приходящих в вершину; источник — вершина с нулевой входящей степенью;
топологический порядок — перестановка вершин, согласованная со всеми рёбрами.

**Что объяснить:** как меняются входящие степени и очередь, почему можно выбрать
любой доступный источник, как учитываются параллельные рёбра и зачем проверять
число обработанных вершин, даже если часть графа уже отсортирована.

**Вопросы преподавателя:**

1. Почему вершину с нулевой степенью можно взять следующей? У неё нет
   необработанных предшественников, которые обязаны стоять раньше.
2. Почему остаток без источников содержит цикл? Переходя по входящим рёбрам
   внутри конечного остатка, мы обязательно повторим вершину.
3. Можно ли вернуть уже построенную часть при цикле? Нет, это не порядок всех
   вершин; метод выбрасывает исключение.
4. Зачем проверять не только `position[u] < position[v]`? Иначе можно пропустить
   отсутствие изолированных вершин, повторы или неверные номера в массиве.
5. Чем очередь отличается от стека Kosaraju? Здесь вершины готовы к обработке
   по зависимостям; очередь не хранит текущий путь DFS, поэтому `maxDepth = 0`.

### PATH — расстояния, релаксация и восстановление пути

**Файлы для копирования в чат:** `src/main/java/algorithms/DagShortestPath.java`,
`src/main/java/algorithms/PathResult.java`, `src/main/java/algorithms/Kahn.java`,
`src/main/java/graph/Graph.java`, `src/main/java/graph/Edge.java`,
`src/main/java/metrics/Metrics.java`, `src/test/java/algorithms/DagShortestPathTest.java`,
`data/dag-directed.txt`.

**Классы и методы:** `DagShortestPath.compute`; `PathResult.distanceTo`,
`parentOf`, `distances`, `parents`, `pathTo`, `edgePathTo`, `sumDistances`;
`Kahn.compute`; `DagShortestPathTest.bellmanFord`, `assertPaths`.

**Задача:** для каждой вершины DAG найти минимальный вес пути от любого источника.
Топологический порядок гарантирует обработку всех предшественников до вершины.
При улучшении расстояния сохраняются родитель и конкретное ребро.
По родителям можно восстановить выбранный путь назад и затем развернуть его.

**Термины:** релаксация — попытка улучшить расстояние через ребро; виртуальный
общий источник — модель нулевого старта у всех исходных источников; бесконечность —
метка ещё не найденного расстояния; предшественник — предыдущая вершина выбранного
пути; отрицательный цикл — цикл с отрицательной суммой весов.

**Что объяснить:** почему нулём инициализируются только источники, почему хватает
одного прохода по топологическому порядку, как восстанавливается путь и зачем
для параллельных рёбер хранится `parentEdge` в дополнение к `parent`.

**Вопросы преподавателя:**

1. Почему нельзя присвоить ноль всем вершинам? Это разрешило бы начинать путь
   в любой вершине и дало бы неверные ответы, например 0 вместо 7 на ребре веса 7.
2. Почему один проход достаточен? К обработке вершины уже известны окончательные
   расстояния до всех её предшественников, а последующие вершины не ведут назад.
3. Почему допустимы отрицательные веса? В DAG нет циклов, поэтому нельзя повторять
   отрицательный цикл; порядок обработки не зависит от знака веса.
4. Зачем нужен `long`? Даже несколько рёбер с весом `Integer.MAX_VALUE` дают
   расстояние больше максимального `int`; с бесконечностью вес не складывается.
5. Почему одного `parent[]` мало для точного веса восстановленного пути?
   Между одной парой вершин могут быть рёбра разных весов, поэтому сохраняется
   конкретное ребро последнего улучшения.

DSU сравнивается с метками множеств, MST — между двумя алгоритмами и с полным
перебором, SCC — со взаимной достижимостью через BFS, пути — с Bellman–Ford.
Фиксированные seed делают случайные примеры повторяемыми, а отдельные тесты
закрывают граничные случаи, счётчики и большие графы.

**Термины:** эталон — простая независимая реализация для сравнения;
seed — начальное состояние генератора; инвариант — свойство корректного
результата, например `n-components` рёбер леса; регрессионный тест — проверка,
которая помогает обнаружить возвращение ранее устранённой ошибки.

**Что объяснить:** чем сравнение с независимым эталоном сильнее одной проверки
на известном примере, почему номера SCC могут различаться и почему совпадение
весов MST дополняется проверкой структуры леса.

**Вопросы преподавателя:**

1. Почему Kruskal и Prim недостаточно просто сравнить друг с другом? В обоих
   может быть ошибка; маленькие графы дополнительно проверяются полным перебором.
2. Что проверяет BFS для SCC? Для каждой пары наличие пути в обе стороны должно
   совпадать с принадлежностью одной компоненте.
3. Почему Bellman–Ford начинает с нескольких нулевых расстояний? Эталон должен
   решать ту же задачу с виртуальным общим источником.
4. Зачем фиксировать seed? Чтобы повторный запуск воспроизвёл тот же граф
   и возможную ошибку.
5. Как запустить проверки? `mvn test` запускает все; например,
   `mvn -Dtest=DagShortestPathTest test` запускает только проверки путей.

CSV записывается только после успешного прохождения всех проверок.

**Термины:** медиана — средний элемент отсортированных пяти измерений; эталон —

вызовов, что входит в таймер, почему нельзя суммировать счётчики пяти запусков
и как программа обнаруживает неверный результат.

**Вопросы преподавателя:**

1. Почему 50 строк? Пять размеров × две плотности × пять алгоритмов.
2. Почему DSU не отдельная строка? Его работа входит в Kruskal; таблица требует
   пять графовых алгоритмов.
3. Почему таблица не подменяет вычисления? Эталон вызывается после алгоритма
   только для сравнения; в CSV записан результат алгоритма.
4. Что будет при несовпадении? Исключение, ненулевой код выхода и отсутствие
   перезаписи итогового CSV этим запуском.
5. Какие накладные расходы исключены из времени? Генерация, валидация, сумма
   расстояний и запись CSV; подготовка внутри алгоритмов включена.

### TARJAN — один DFS и стек активных вершин

**Файлы для копирования в чат:** `src/main/java/algorithms/Tarjan.java`,
`src/main/java/algorithms/SccResult.java`, `src/main/java/algorithms/Kosaraju.java`,
`src/test/java/algorithms/TarjanTest.java`, `src/main/java/benchmark/BonusBenchmark.java`.

**Классы и методы:** `Tarjan.compute`, `SccResult.samePartitionAs`,
`TarjanTest.check`, `BonusBenchmark.main`.

**Задача:** найти то же разбиение SCC одним обходом исходного графа.
Индексы и lowlink показывают, может ли вершина связаться с более ранней активной
частью обхода. Когда найден корень SCC, её вершины снимаются со второго стека.
Явный стек кадров позволяет обойти большой граф без рекурсии.

**Термины:** index — номер открытия; lowlink — наименьший достижимый активный
индекс по правилам Tarjan; активная вершина — ещё не назначенная завершённой SCC;
корень SCC — вершина с равными index и lowlink.

**Что объяснить:** различие двух стеков, обновление lowlink после потомка,
игнорирование рёбер в завершённые SCC и сравнение произвольных меток компонент.

**Вопросы преподавателя:**

1. Почему не нужен обратный граф? Lowlink и активный стек позволяют определить
   границы SCC в исходном DFS.
2. Почему нельзя обновлять lowlink по любому посещённому соседу? Сосед может
   принадлежать уже закрытой SCC, которую нельзя объединять с текущей.
3. Почему нужен второй стек? Завершённый кадр DFS может оставаться частью ещё
   не закрытой SCC.
4. Сколько рёбер просматривается? `m`, каждое исходящее ребро один раз.
5. Как проверяется совпадение с Kosaraju? Через биекцию меток компонент,
   а в небольших тестах ещё и сравнением принадлежности каждой пары вершин.

### CRITICAL — конденсация и критическая цепочка

**Файлы для копирования в чат:** `src/main/java/algorithms/Condensation.java`,
`src/main/java/algorithms/CriticalPath.java`, `src/main/java/algorithms/Tarjan.java`,
`src/main/java/algorithms/Kahn.java`, `src/test/java/algorithms/CriticalPathTest.java`,
`src/main/java/benchmark/BonusBenchmark.java`, `results/bonus.csv`.

**Классы и методы:** `Condensation.build`, `durationOf`, `components`;
`CriticalPath.compute`, `CriticalPath.Result.duration`, `componentPath`, `finishTimes`;
`BonusBenchmark.validateCritical`; `CriticalPathTest.enumeratePaths`.

**Задача:** представить SCC как блоки и найти самую долгую цепочку зависимостей.
Длительность блока равна числу вершин, исходные веса рёбер игнорируются.
Максимальные времена завершения распространяются по DAG в топологическом порядке.
Родители позволяют восстановить цепочку, определяющую общее время при
неограниченном параллелизме независимых блоков.

**Термины:** конденсация — граф SCC; длительность — вес вершины-блока;
критический путь — цепочка максимальной суммарной длительности; нулевая задержка —
зависимость без дополнительного времени на ребре.

**Что объяснить:** почему конденсация ациклична, почему нужно учитывать длительность
источника, как максимум связан с минимумом при смене знака и почему исходные циклы
нельзя считать автоматически разрешёнными в реальном планировщике.

**Вопросы преподавателя:**

1. Почему конденсация — DAG? Цикл между SCC означал бы взаимную достижимость
   и одну общую SCC вместо нескольких.
2. Что является весом? Число исходных вершин в блоке; рёбра имеют нулевую задержку.
3. Почему задача проста на DAG? Все предшественники обработаны до вершины;
   для длиннейшего простого пути общего графа такого порядка нет, задача NP-трудна.
4. Где используется критический путь? В оценке минимального срока проекта
   с зависимостями при достаточных ресурсах для параллельных работ.
5. Почему результаты не в основных 50 строках? Это отдельная бонусная модель,
   её результаты и размеры конденсации нельзя смешивать с обязательной таблицей.
